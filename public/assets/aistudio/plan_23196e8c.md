# Web Server & Thin Launcher Streaming Architecture (`plan.md`)

## 1. Objective & Separation of Concerns

Separate the distributed client into two strictly isolated components so that **no module code, offsets, scanner logic, or overlay logic is ever compiled into or stored inside the distributed launcher**:

1. **Thin Launcher (`d9a-launcher`)** — Distributed to end users.
   - Contains **only**: frameless Win32 GUI (Sign In, Redeem Code, Game Library), HTTPS/HTTP client, session token handling, ChaCha20-Poly1305 AEAD decryption (`d9a-proto`), and in-memory module loading + buffer zeroization.
   - Contains **zero** game offsets, scanner code, targeting logic, overlay rendering, or embedded binaries.
2. **Module Artifacts (`d9a-module-*.dll`)** — Hosted exclusively on the server (local machine or website-attached delivery server).
   - Built as `cdylib` targets containing the game-specific visual/targeting/scanner modules.
   - Stored in a private server-side vault directory (e.g., `server_vault/tarkov_x64.bin`), never exposed as static public web files.
3. **Web Server & Delivery API (`d9a-server` + Website)** — Runs on a local host or a server attached to the website.
   - Serves the public website (storefront, key purchasing, account management, thin launcher download).
   - Serves the authenticated delivery API that validates licenses, checks expiration, encrypts the requested module per-session, and streams it directly to the launcher.

## 2. System Architecture & Streaming Flow

```
[ End User ]
     │
     ▼
[ Thin Launcher (d9a-launcher.exe) ]   <-- No module code bundled
     │  1. POST /api/login or /api/redeem (credentials / key)
     │  2. Receives session_token + entitled game list + expiry
     │  3. User selects game in Game Library
     │  4. POST /api/stream (session_token, game_id, client_nonce)
     ▼
[ Website / Delivery Server (d9a-server) ]
     │  5. Verifies session_token & license expiry in SQLite (d9a_licenses.db)
     │  6. Verifies user entitlement for requested game_id
     │  7. Reads module artifact from private server_vault/
     │  8. Encrypts module bytes with per-session ChaCha20-Poly1305 AEAD key
     │  9. Streams encrypted block with explicit Content-Length
     ▼
[ Thin Launcher (in memory) ]
     │ 10. Receives encrypted bytes into Zeroizing<Vec<u8>>
     │ 11. Verifies AEAD tag & decrypts into memory buffer
     │ 12. Loads & initializes module in memory (no standalone file written to disk)
     │ 13. Zeroes plaintext and ciphertext buffers immediately after load
```

## 3. Workspace & Crate Layout

| Crate / Directory | Role | Distributed to Users? |
|---|---|---|
| `crates/d9a-proto` | Shared DTOs (`LoginRequest`, `RedeemRequest`, `StreamRequest`, `StreamResponse`), ChaCha20-Poly1305 AEAD seal/open, `Zeroizing` buffer helpers | Shared library |
| `crates/d9a-launcher` | Thin GUI launcher (Sign In, Redeem, Game Library, stream client, in-memory loader). Stripped release binary (`strip = true`, `lto = true`, `panic = "abort"`). | **Yes** (`d9a-launcher.exe`) |
| `crates/d9a-module-tarkov` | `cdylib` exporting `d9a_module_entry(ctx)` containing scanner, overlay, config, and targeting logic (moved out of `d9a-client`). | **No** — streamed from server only |
| `crates/d9a-server` | Licensing, SQLite key vault (`d9a_licenses.db`), web storefront static/API routes, and authenticated encrypted module streaming (`/api/stream`). | **No** — server-side only |
| `web/` | Website frontend (landing page, pricing/code purchase, account portal, launcher download link). | Served by `d9a-server` or reverse proxy |
| `server_vault/` | Private directory holding compiled `d9a_module_*.dll` artifacts (excluded from static web root). | **No** — server-side only |

## 4. Server & Website Setup

### 4.1 Hosting Modes
- **Local Machine Mode**: `d9a-server` binds to `127.0.0.1:8443` (or LAN IP `0.0.0.0:8443` with firewall rules) for local testing and private streaming.
- **Website-Attached Server Mode**: `d9a-server` runs behind a TLS-terminating reverse proxy (Caddy or Nginx) on the production domain (e.g., `https://api.d9assist.com` / `https://d9assist.com`), with automatic HTTPS certificates and rate limiting.

### 4.2 API Endpoints (`d9a-server`)
| Endpoint | Method | Purpose |
|---|---|---|
| `/` & `/assets/*` | `GET` | Public website storefront, pricing, and thin launcher download. |
| `/api/redeem` | `POST` | Validates activation code, binds username + Argon2 password hash to the code, sets expiration timestamp (`Week`, `Month`, `Year`, `Lifetime`). |
| `/api/login` | `POST` | Verifies credentials and license expiration; issues signed/random `session_token` and returns entitled games list. |
| `/api/library` | `POST` | Returns active games, version metadata, and license status for a valid `session_token`. |
| `/api/stream` | `POST` | Validates `session_token`, expiry, and game entitlement; reads `server_vault/<game_id>.dll`, encrypts with session AEAD key + fresh nonce, and streams the encrypted block with explicit `Content-Length`. |
| `/api/admin/mint` | `POST` | Admin-authenticated endpoint (or CLI subcommand) to generate new activation codes and revoke expired/abused keys. |

## 5. Thin Launcher Implementation Plan

1. **Extract Module Code out of `d9a-client`**:
   - Move `scanner.rs`, `overlay.rs`, `items_db.rs`, `targeting.rs`, `math.rs`, `config.rs`, and `targets/` into `crates/d9a-module-tarkov` (`crate-type = ["cdylib"]`).
   - Expose a single C-ABI entry point `pub extern "C" fn d9a_entry(session_ptr: *const u8, session_len: usize) -> i32`.
2. **Slim `d9a-launcher` (or refactor `d9a-client`)**:
   - Keep only `main.rs` (`#![windows_subsystem = "windows"]`), `delivery.rs` (GUI Auth + Game Library + HTTPS/HTTP streaming client), and the in-memory loader.
   - Configure delivery endpoint via build-time or config constant (e.g., `D9A_SERVER_URL`, defaulting to `http://127.0.0.1:8443` for local dev and `https://<domain>` for release).
3. **In-Memory Decryption & Cleanup**:
   - Read streamed ciphertext into `Zeroizing<Vec<u8>>`.
   - Decrypt with `d9a_proto::open_block` into a `Zeroizing<Vec<u8>>` plaintext buffer.
   - Map/execute the module in memory without saving any `.dll` or `.exe` to disk.
   - Drop/zero both ciphertext and plaintext buffers immediately after handoff.
4. **Release Hardening**:
   - Workspace `[profile.release]`: `opt-level = "z"` or `3`, `lto = true`, `codegen-units = 1`, `strip = "symbols"`, `panic = "abort"`.
   - Verify with `strings` / `dumpbin` that `d9a-launcher.exe` contains zero game offsets, item IDs, or scanner strings.

## 6. Verification Steps

1. Start `d9a-server` locally with a compiled `server_vault/tarkov_x64.dll`.
2. Launch `d9a-launcher.exe`: verify sign-in, redeem, and Game Library UI with zero console window.
3. Click **Launch** on Escape From Tarkov: verify `/api/stream` delivers the encrypted block, launcher decrypts and loads it in memory, and no module file is written to disk.
4. Verify expired or invalid session tokens receive `401 Unauthorized` / `403 Forbidden` from `/api/stream`.
5. Inspect `d9a-launcher.exe` binary to confirm zero module symbols or game offsets are embedded.
